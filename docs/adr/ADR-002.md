# Vue.js как frontend-фреймворк

## Контекст и постановка задачи

Интерфейс сервиса включает каталог с фильтрами, карточки фильмов, формы оценок и рецензий, подборки, администрирование и персональную ленту (SYS-F-04…SYS-F-09, SYS-F-14, SYS-F-16, SYS-F-22). Требуется обеспечить адаптивность, клавиатурную навигацию и контраст (SYS-NF-06) при ограниченном фронтенд-ресурсе – один специалист на 12 недель. Необходимо выбрать подход к построению UI, совместимый с REST API на C++/Drogon и дающий предсказуемое время разработки. Проектные представления: DV-03, DV-05, DV-08.

## Драйверы решения

* Один frontend-специалист и жёсткий срок 12 недель.
* Развитая интерактивность фильтров, подборок и ленты без полной перезагрузки страницы.
* Требования доступности: адаптивная вёрстка, клавиатурная навигация, контраст (SYS-NF-06).
* Чёткое разделение: сервер отдаёт REST/JSON, клиент отвечает за представление.
* Необходимость переиспользования компонентов карточки фильма и оценки.
* Ограничение CI: один дополнительный шаг сборки frontend.

## Рассмотренные варианты

* Vue.js 3 с Bootstrap 5 и сборкой через Vite.
* Серверный HTML с HTMX и Bootstrap 5.
* React с REST API.

## Итог решения

Выбран вариант «Vue.js 3 с Bootstrap 5», потому что компонентная модель позволяет быстро собрать фильтры, карточки, подборки и ленту, а реактивное состояние упрощает сценарии с объяснениями рекомендаций. HTMX ограничен в сложных сценариях подборок и дайджеста, а React требует более тяжёлой конфигурации и большего времени на тестирование при одном frontend-разработчике. Сервер остаётся источником бизнес-логики и валидации.

### Последствия

* Хорошо, потому что компоненты карточки фильма, оценки и подборки переиспользуются между экранами.
* Хорошо, потому что REST-контракт из DV-05 остаётся единственным способом взаимодействия клиента и сервера.
* Плохо, потому что появляется отдельная сборка Vite и дополнительный шаг в CI.
* Плохо, потому что валидация должна дублироваться на клиенте для UX и на сервере для безопасности.

### Подтверждение

Соответствие проверяется на демо итераций 2 и 5, осмотром разметки (I), автоматическими проверками контраста и наличия aria-атрибутов. Сборка Vite включается в CI и считается обязательной для релиза. Нагрузочный тест NF-01 подтверждает, что REST API укладывается в p95 ≤ 500 мс.

## Плюсы и минусы вариантов

### Vue.js 3 с Bootstrap 5

* Хорошо, потому что обеспечивает реактивные фильтры и подборки без перезагрузки страницы.
* Хорошо, потому что компоненты легко тестировать и переиспользовать.
* Нейтрально, потому что требует REST API, уже описанного в DV-05.
* Плохо, потому что добавляет шаг сборки frontend в CI.

### Серверный HTML с HTMX

* Хорошо, потому что не требует отдельной JS-сборки.
* Хорошо, потому что бизнес-логика полностью остаётся на сервере.
* Нейтрально, потому что подходит для простых фильтров каталога.
* Плохо, потому что неудобен для сложного состояния подборок и дайджеста.

### React

* Хорошо, потому что имеет развитую экосистему и инструменты тестирования.
* Нейтрально, потому что также использует REST API.
* Плохо, потому что требует более сложной конфигурации и большего объёма кода.
* Плохо, потому что не укладывается в доступный frontend-ресурс.

## Дополнительная информация

Первоначально 02.11.2026 был выбран HTMX. Решение пересмотрено 19.11.2026 после CR-04: подборки и дайджест требуют развитого состояния интерфейса. Текущий выбор – Vue.js 3. Пересмотр требуется при появлении мобильного приложения или отказе от REST API в пользу GraphQL. Связанные решения: ADR-001, ADR-005.
