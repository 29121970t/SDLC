# Адаптер TMDB с импортом только по идентификатору

## Контекст и постановка задачи

Администратор наполняет каталог метаданными фильмов через SYS-F-17. Источник – TMDB API, доступный по HTTPS. Первоначально планировались поиск по названию, выбор из нескольких результатов, загрузка постеров и дедупликация за 11 человеко-дней. После CR-02 объём сокращён до 8 человеко-дней: в MVP импорт выполняется по TMDB ID с предпросмотром. Требуется зафиксировать контракт адаптера, правила кэширования и поведение при недоступности сервиса (SYS-NF-03). Проектные представления: DV-05, DV-07.

## Драйверы решения

* Таймаут запроса 3 с, кэш не менее 24 ч и fallback на локальные данные (SYS-NF-03).
* Ограничение TMDB по частоте запросов и формату ответов.
* Сокращение объёма на 3 человеко-дня после CR-02.
* Необходимость предпросмотра перед сохранением в каталог.
* Дедупликация по TMDB ID и обновление существующих записей.

## Рассмотренные варианты

* Адаптер TMDB с импортом по ID и предпросмотром.
* Импорт по поисковому запросу с выбором результата.
* Прямые HTTP-запросы к TMDB из административного интерфейса без адаптера.

## Итог решения

Выбран «Адаптер TMDB с импортом по ID и предпросмотром», потому что он покрывает потребности контент-команды в MVP и стоит 8 человеко-дней. Поисковый сценарий требует обработки неоднозначных результатов и дополнительного тестирования; он перенесён в релиз 2. Прямые запросы из UI нарушили бы границы модулей ADR-001 и не позволили бы применить единый таймаут и кэш.

### Последствия

* Хорошо, потому что контент-команда может быстро добавить фильм, вставив ID со страницы TMDB.
* Хорошо, потому что кэш Redis и fallback снижают зависимость от доступности внешнего API.
* Плохо, потому что администратор должен самостоятельно находить корректный TMDB ID.
* Плохо, потому что поиск по актёрам SYS-F-24 реализуется по локальным данным каталога, а не через TMDB.

### Подтверждение

Контракт проверяется интеграционными тестами с mock TMDB, нагрузочным тестом NF-03 и ревью логов. Наличие таймаута 3 с и TTL 24 ч подтверждается конфигурацией и тестом деградации внешнего сервиса.

## Плюсы и минусы вариантов

### Импорт по ID

* Хорошо, потому что стоит 8 человеко-дней вместо 11.
* Хорошо, потому что предпросмотр исключает случайную запись неверного фильма.
* Нейтрально, потому что ID можно найти на сайте TMDB вручную.
* Плохо, потому что поиск по названию доступен только в релизе 2.

### Импорт по поисковому запросу

* Хорошо, потому что упрощает работу администратора.
* Нейтрально, потому что использует тот же адаптер.
* Плохо, потому что требует 11 человеко-дней и сценария выбора.
* Плохо, потому что неоднозначные результаты усложняют тестирование.

### Прямые запросы из UI

* Хорошо, потому что не требует серверного кода.
* Нейтрально, потому что быстро прототипируется.
* Плохо, потому что нарушает границы модулей ADR-001.
* Плохо, потому что не позволяет применить общий кэш, таймаут и логирование.

## Дополнительная информация

Решение принято 05.11.2026 на основании CR-02 и писем 2–5 первого раунда. Ограничение «import by ID only» действует в MVP. CR-04 добавил SYS-F-24, который использует локальные данные актёров и режиссёров. Пересмотр требуется при переходе к релизу 2 или изменении условий TMDB API. Связанные решения: ADR-003, ADR-005.
